# Task prompt review (#1253)

In run 2 (Nov 5–9, 3 models × 2 trials), every setup passed almost every task. `barebones` (winapp hidden, no skills) passed 77 of 78 runs of the 13 normal tasks, `cli-only` 78 of 78, and `cli-plus-skills` 77 of 78. A task that every setup passes can't show whether winapp or the skills help.

One suspected cause was that the prompts name the answer, for example "sign this file with this pfx". This review checks each prompt for that, rewrites the ones that give the method away, and moves the method into a `reference` field in `task.json` that the agent never sees. The pass counts below are run-2 results with the *old* prompts.

`asks-before-elevating` is a safety task with its own rules and is left as is.

## Notes

- **Most prompts didn't give the answer away.** Eight of the 13 normal tasks already described the outcome, and `barebones` still passed them. So naming the answer is not the main reason the tasks can't tell setups apart. The models already know how to do these jobs with the Windows SDK, PowerShell and plain XML: in run 2, `barebones` wrote App Installer XML, manifest extensions and certificate imports by hand.
- **Only three rewrites remove a real giveaway:** `sign-with-pfx` (the action), `wpf-identity-toast` (the diagnosis) and `ui-order-total` (the click-by-click steps). The others are small wording changes.
- **Expect the rewrites to change little.** Run them before drawing conclusions, but if `barebones` stays at 90% or more, the task is a sanity check and stays out of the headline.
- **Run-2 results are not comparable with the new prompts.** Compare only runs made with the same prompt wording.

### Checks that test the method instead of the outcome

- `wpf-identity-toast`: `identity-registered` and `has-identity` require package identity, not only a working toast. An agent could instead pass an app ID to `CreateToastNotifier`, and the toast would work but the task would fail. The new prompt says not to change the notification code, which leaves identity as the only fix, so the checks match the prompt. No checker change.
- `install-untrusted`: `package-unchanged` (fix by trusting the signer, not by re-signing) is a method preference, but it is an improvement check, not required. No change.
- `winforms-msix`, `electron-msix`: `msix-signed` is required although the prompt no longer says "signed". The `.msix` can't be installed from the file without a signature, so the outcome implies it. No change.
- No other check depends on the method. `appinstaller-every-launch` checks `HoursBetweenUpdateChecks="0"`, which is how App Installer encodes "every launch".

### Tasks that need a redesign, not a prompt rewrite

These passed every `barebones` run, and the prompt wasn't the reason. A new version needs a job that is hard without winapp or the skills, for example one with several steps where a mistake in one shows up only later, or a failure whose cause isn't in the error text.

- `exec-alias`, `startup-task`, `file-association`, `winforms-msix`, `electron-msix`: a manifest edit plus pack, sign and install. The models know the manifest XML and the SDK tools.
- `appinstaller-update`: one well-documented XML file.
- `install-untrusted`, `publisher-mismatch`: the error code leads straight to a well-known fix.
- `manifest-pack-error`: `makeappx` reports both problems clearly, one at a time.
- `winui-new`: the WinUI templates install with `dotnet new install`, so `barebones` scaffolds without winapp.
- `ui-order-total`: PowerShell can drive the app through UI Automation, and the app is a single simple window.
- `sign-with-pfx`, `wpf-identity-toast`: the rewrite removes the giveaway, but both have a short, well-known fix. Redesign if `barebones` still passes them.
